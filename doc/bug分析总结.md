# Bug 分析总结：AI 助手"查不到数据"偶发回归

> 项目：高校任务管理系统（多租户 SaaS）AI 助手模块
> 技术栈：Spring Boot 2.5 + GLM-4.5-Air（Function Calling）+ uni-app H5
> 修复提交：`ba33aee`（2026-09）

---

## 一、问题现象

用户反馈：**"在你修改之前，提问题可以查很多数据并且有很好的回复，修改之后就变成了查不到"**。

- 修改前：问"查全部任务" → 返回 142 条任务，带可点击的详情链接；
- 修改后：问"查下全部任务" → 返回"抱歉，这个问题我没有查到真实数据，不能凭空回答"，下方只剩 [查任务] [查会议] [查重点工作] 三个引导按钮。

典型的"改了 A，坏了 B"的回归报告——而且**同样的问法有时正常、有时失败**，不是必现问题。

## 二、排查过程（面试重点：怎么定位的）

### 第 1 步：先确认失败路径，而不是瞎猜

截图里那句"没有查到真实数据"的文案 + 三个固定引导按钮，和后端代码里的**防幻觉兜底分支**完全吻合：

```java
// AiChatService.doChat
boolean fabricated = toolsCalled == 0 && looksLikeFabricatedData(answer);
if (fabricated) {
    answer = "抱歉，这个问题我没有查到真实数据，不能凭空回答……";
    // 选项被替换为 查任务/查会议/查重点工作
}
```

触发条件是**本轮一次查询工具都没调用（toolsCalled == 0），但回答却长得像数据列表**。
所以问题转化为：**那一轮模型为什么没调工具就输出了列表？**

> 经验：报错文案是"指纹"。先在代码里全文检索用户看到的文案，确定是哪条分支发出的，比从"最近改了什么"开始猜效率高得多。

### 第 2 步：直接复现——结果复现不了

用同样的问法"查下全部任务"/"查全部任务"打了 3 次 `/ai/chat` 接口，**全部正常返回 142 条**。
说明输入文本本身没问题，问题依赖**某个上下文条件**，是偶发/条件触发。

### 第 3 步：从数据库还原真实现场（关键一步）

用户是流式对话，接口参数没有留存。但每轮问答都落在 `ai_chat_message` 表里，于是把该账号全部 7 个会话拉出来扫描"没有查到真实数据"这个指纹，命中会话 `6a67f5ed`：

```
[用户]   查任务
[助手]   您想查询什么时间范围的任务？        ← 意图门控追问
[用户]   查全部任务
[助手]   共142条任务，前10条……            ← 正常
[用户]   按负责人筛选
[助手]   请选择负责人（也可以直接说出姓名）：  ← 筛选菜单
[用户]   周水红
[助手]   共20条周水红负责的任务，前10条……   ← 正常
[用户]   查下全部任务                       ← 手动输入
[助手]   抱歉，这个问题我没有查到真实数据……  ← 失败！
[用户]   查下全部任务                       ← 用户重试
[助手]   抱歉，这个问题我没有查到真实数据……  ← 又失败！
```

对比发现：**同样的"查下全部任务"，在"周水红任务列表"这个上文之后连续失败 2 次；在其它上下文（甚至同一个会话早些时候）里都成功**。

### 第 4 步：带着完整上下文复现——抓到另一种形态

把这个 8 条消息的历史原样塞回接口重放 3 次，出现了一个**新的坏形态**：

- 回答内容是"共142条任务……"，看起来完全正常；
- 但 `tasks` 字段是 **0**（正常应为 10，前端靠它渲染可点击链接）。

也就是说模型**没调工具，直接从对话历史里把旧列表抄了一遍**——数据碰巧是真的（历史就是真数据），但抄出来的回答没有链接。

### 第 5 步：根因收敛

两种失败形态同源：

| 形态 | 用户看到 | 原因 |
|------|---------|------|
| 编造/改写列表，多行编号 | "没有查到真实数据"（被兜底拦截） | 零工具调用 + `numbered >= 2` 判定命中 |
| 原样复述历史，压缩成一行 | "真数据"但**没有链接** | 零工具调用 + 行首编号计数为 0，判定**漏过** |

**根因：当对话历史里带着列表数据 + 存在"独立新查询"注入语时，模型有较大概率跳过 Function Calling，直接复述上文列表。**而最近的几次改动（防上下文污染的注入语、常驻参考层让 system prompt 里也有数据清单、切换到 glm-4.5-air）都提高了这个概率——这就是用户感觉"改了之后变差"的原因：不是某次修改写错了逻辑，而是**修改改变了模型的行为分布，把一个潜伏问题放大到了用户可感知**。

## 三、解决方案（机制性修复，不依赖模型自觉）

面试时强调的设计原则：**提示词只是软约束，凡是要保证的行为必须由代码机制兜底。**

### 修复 1：零工具调用 → 自动纠错重试，而不是直接判死

原来是"检测到编造 → 替换为兜底文案"，用户得到的是一次失败体验。
改成：检测到"查询类问题 + 零工具调用"时，把模型的错误回答留在消息流里，注入一条纠错指令再调一次模型：

```java
if (toolsCalled == 0 && !retrievalNudgeUsed && looksLikeDataRequest(effectiveMessage)) {
    retrievalNudgeUsed = true;
    messages.add(respMsg);   // 保留模型的"错误答案"
    messages.add(new JSONObject().set("role", "user").set("content",
            "你上一条回答没有调用任何查询工具，其中的列表内容不是本次查询的真实结果"
          + "（可能是复述了上文或凭印象生成）。请重新调用工具查询真实数据后作答……"));
    answer = null;
    continue;                // 再走一轮
}
```

细节：
- **每轮对话最多重试一次**（`retrievalNudgeUsed` 标志），避免死循环和多付一次 token；
- 只对**查询类问题**（`looksLikeDataRequest`：含"查/列出/有哪些"或识别到业务模块）重试——闲聊类问题零工具调用是正常的，不该重试；
- 重试后仍不调工具，才落回原来的防幻觉兜底。

效果：模型第一次偷懒时被自动拉回，用户无感知；真正无法查询的场景仍然诚实告知。

### 修复 2：堵住"单行压缩列表"的识别漏洞

原判定只数**行首**编号（`^\d[.、]`），模型把列表压成一行就漏过。补上行内模式：

```java
// "1. xxx  2. xxx"挤在一行：数行内编号标记，阈值 4 个避开日期"2026.5"之类误伤
private static final Pattern INLINE_NUMBERED = Pattern.compile("\\s[1-9][0-9]?[.、．]");
```

### 修复 3：注入语强化（软约束补充）

"独立新查询"注入语追加："上文出现过的列表数据已过时，必须重新调用工具查询，禁止直接复述上文内容"——降低第一次就跳工具的概率，和修复 1 双保险。

## 四、验证

用失败现场的完整历史（周水红列表 → 查下全部任务）重放：

- 修复前：多行编造 → 兜底"查不到"（用户截图）；单行复述 → 无链接假正常（tasks=0）；
- 修复后：**3/3 通过**——142 条任务、`tasks=10`（带链接）、正常选项。

回归抽查全部正常：查下本周的任务（45 条）、李慧秋的任务（20 条）、查下最近的会议（如实回答"近期无会议"，没有编数据）。

## 五、延伸讨论：能不能复用上一轮的查询结果？（面试高频追问）

修复方案出来后有个自然的反问：**上轮已经查出 142 条任务了，用户再问时模型直接复用上文列表、不再查库，听起来也挺合理啊？** 结论是：这个优化对人和程序成立，对 LLM 恰恰不成立。

### 1. 模型的"复用"不是缓存，是有损重新生成

人想象的复用是程序取缓存：字节级原样取回，零损耗。但 LLM 做的是**照着上文重新生成一段"像列表"的东西**——每个数字、每个名字、每个日期都是逐 token 重新生成的：142 可能抄成 143，"陈慧"可能串成上上文的"李慧秋"。哪怕上文 100% 是真数据，模型复述出来的版本也是一次新的掷骰子。**生成式模型的"记忆"没有拷贝语义**——这是它和缓存的本质区别，也是本 bug 里"抄历史"形态仍然必须拦截的根本原因。

### 2. 即使抄对了，还有两个实际代价

- **新鲜度不可控**：多用户系统里，两轮对话之间别的用户可能刚建了任务、改了状态。用户再问一次，期待的是"现在"的状态；领导层拿旧数据做判断有业务风险，且用户无法察觉数据是旧的。
- **链接必然断**：前端可点击链接靠 `tasks` 数组，它只来自工具调用的结构化返回。模型抄历史的那一轮 `tasks=0`——正是本 bug 中"数据看着对但没有链接"的形态。

### 3. 幻觉识别的难点与出路：识别"来源"，不识别"内容"

"识别是否幻觉"之所以难，是因为本能地想从**内容**判断（这段话像不像真的）。但编造的列表和真实的列表在语言形态上没有区别——模型编的时候语气一样笃定、格式一样工整，内容层面的识别天然不可靠。

所以本方案换了个信号：**看出处，不看内容**。代码只问一个问题——"这段数据有没有一次真实的数据库查询可以追溯？"零工具调用却给出数据式回答 = 来源不存在 = 按编造处理。识别从"对文本做猜测"退化成了一个确定性的计数问题（`toolsCalled == 0`）。

### 4. 真想省这次查询，应该在确定性层做

复用的诉求合理（省时省 token），但应发生在**工具层**而不是概率层：

- **工具层短 TTL 缓存**（30~60 秒）：同样的查询条件直接返回缓存结果，跳过 SQL。模型照常"调工具"，只是工具内部命中缓存——每轮依然有结构化返回、链接完好、对模型透明。
- 分层原则：**让概率性的模型只负责理解意图，让确定性的代码负责持有数据**。数据的 fidelity 永远不能托付给生成过程。

### 5. 误判成本不对称：宁可多查一次，不可放出一条假数据

- 误杀（真数据被当编造）→ 多查一次库，用户基本无感知；
- 漏放（编的数据流出去）→ 用户基于假数据做判断，对系统的信任崩塌。

所以整套设计偏向误杀：纠错重试拉回工具 → 仍不调 → 宁可说"没查到"也不放行。也不做"内容与历史相似度对比"之类的判定——那又回到了内容识别的老路，且两类误判都有害。

> 一句话总结：LLM 应用里，回答中的业务数据必须能追溯到一次真实查询；想省查询，在工具层做缓存，而不是让模型凭上下文"背"出来——因为模型的复述是重新生成，不是拷贝。

## 六、复盘要点（面试话术）

1. **报错文案是定位入口**：先确定输出来源分支，把"用户体验问题"翻译成"哪段代码在什么条件下执行"。
2. **复现不了就去查存储**：接口是无状态的，但对话落库了——从 DB 还原用户真实上下文，比反复换问法猜条件可靠得多。
3. **偶发问题也是确定性问题**：不是"模型玄学"，是"特定上下文 + 特定注入语"下的条件触发，找到那个条件就能稳定复现。
4. **LLM 应用的防御性设计**：模型行为是概率分布，代码要按"模型可能不遵守任何指令"来设计——本例的三层防线：注入语引导（软）→ 零工具检测 + 纠错重试（机制兜底）→ 防幻觉替换（最后防线）。
5. **回归的另一种形态**：改代码引入的回归不一定是逻辑写错，也可能是**改变了模型的输入分布，放大了原本低概率的坏行为**——这也是 LLM 应用区别于传统 CRUD 项目的调试难点。
