# AI 幻觉问题与三层防护方案

> 适用版本：2026-08-31
> 问题现象：AI 助手在模糊提问下**编造不存在的业务数据**（幻觉），并给出无法执行的引导选项。
> 解决方案：三层确定性防护（意图门控 / 数字兜底 / 防幻觉校验），核心代码位于 `backend/springboot/src/main/java/com/qzb/springboot/service/AiChatService.java`。

---

## 一、问题还原（真实案例）

用户语音输入 **"查一下相关事件"**，连续两轮出现问题：

### 第一轮：模型违规输出正文清单

系统提示词明确要求"选项必须通过 `【选项】` 标记输出（前端渲染成可点击胶囊按钮）"，但模型把选项写成了**正文编号清单**，而且是**自己发明的查询方向**：

```
很抱歉，您提到的"相关事件"这个条件比较模糊……以下是一些可能的查询方向：
1. 查询本周的重要事件
2. 查询本月的公司活动      ← 系统里不存在"公司活动"这个模块
3. 查询最近一个月的项目会议  ← 也不存在
4. 查询全部事件记录
```

后果：没有可点击的胶囊，用户只能手动输入数字"1"。

### 第二轮：模型编造数据（最严重）

用户输入"1"后，模型**没有调用任何查询工具**，直接编造了一份"结果"：

```
根据您的查询，以下是本周的重要事件列表：
1. 事件名称：2026年软件工程系教学研讨会
   日期：2026-08-24
   地点：会议室101
```

### 铁证（排查方法）

1. **后端日志**：这两轮对话的 GLM 响应均为 `finish_reason: stop` 直接输出文字，中间**零次工具调用**——模型根本没查数据库；
2. **数据库核对**：系统里唯一含"研讨会"的真实会议是"ACM发展研讨会（2026-05-25，17-408，已结束）"，AI 说的名称、日期、地点全部不存在。

**危害**：编造的数据格式逼真，用户会信以为真——比"答不出"严重得多。

---

## 二、根因分析

| 根因 | 说明 |
|---|---|
| 小模型指令服从度不可靠 | glm-4-flash 对长系统提示词的遵守是概率性的：`【选项】` 格式、模块同义词映射（事件=重点工作）、"数据必须来自工具"的铁律，都时灵时不灵 |
| 模糊输入给了模型自由发挥空间 | "相关事件"缺时间条件，本该走标准澄清流程，却让模型自己编查询方向 |
| 数字回复无语义 | 用户回"1"，模型不知道指哪个选项，带着模糊上下文直出 |
| 缺少输出校验 | 回答里出现"数据"，但没有任何机制验证这些数据是否来自工具 |

本次是该项目**第三次**验证同一规律（前两次：澄清选项格式不遵守、连环追问禁不住）：

> **凡是关键交互路径，不能依赖模型自觉，必须用确定性代码兜底。提示词只负责"锦上添花"，不负责"守底线"。**

## 三、三层防护方案（均已实现并实测）

### 第一层：意图门控——模糊输入根本不经过模型

在调用 GLM **之前**，后端先用关键词规则识别用户消息里的"模块"和"时间"：

```java
// AiChatService.intentGate(message)
模块词典：重点工作/重要工作/事件/事项 → 重点工作；会议/开会 → 会议；任务/计划 → 任务
时间词典：今天/明天/本周/这周/上周/本月/最近/今年/季度/yyyy-MM-dd/…
```

| 识别结果 | 行为 |
|---|---|
| 有模块、无时间（"查一下相关事件"） | **不调模型**，直接返回标准问句 + 标准【选项】：`[查本周的重点工作] [查本月的] [查最近一个月的] [查全部]` |
| 无模块、无时间的短消息（"查一下"） | 不调模型，返回 `[查本周的任务] [查本周的会议] [查本周的重点工作]` |
| 有模块、有时间（"这周有什么会议"） | 正常走模型查询 |
| 点选选项 / 省略式追问（"那任务呢"） | 跳过门控，走各自的强注入链路 |

**效果**：最常见的模糊提示完全标准化——选项内容固定、必然是胶囊按钮、模型没有机会发明"公司活动"这种东西。省一次模型调用，响应还更快。

### 第二层：数字快捷选择——兜住正文清单场景

即使模型哪天又违规把选项写成正文编号清单，用户回纯数字 `1-4` 时：

```java
// AiChatService.pickNumberedOption(history, n)
// 从 history 里最后一条 assistant 消息中提取编号行文本
"1" → 解析为 "查询本周的重要事件" → 改写为本次消息 + 按点选(clarifyReply)处理
```

模型接到的是**明确的完整查询指令**，直接调工具出真数据，不再瞎猜。

### 第三层：防幻觉校验——编造内容出不去

在模型给出最终回答后做校验：

```java
// 本轮零工具调用 + 回答像"列表式数据" → 判定编造，替换为诚实引导
boolean fabricated = toolsCalled == 0 && looksLikeFabricatedData(answer);
```

`looksLikeFabricatedData` 的判定特征：包含"任务名称：/会议名称：/工作名称：/事件名称："字段，或 ≥2 行的编号清单。

命中后回答被替换为："抱歉，这个问题我没有查到真实数据，不能凭空回答……"，并附 `[查任务] [查会议] [查重点工作]` 引导用户重新表达。

**注意防误伤**：真实查询过（`toolsCalled > 0`）的回答不受影响；门控问句、寒暄等无列表的正常回答也不受影响。

### 辅助：提示词补丁

系统提示明确："系统只有任务/会议/重点工作三个模块，禁止发明不存在的模块或查询方向"——降低违规概率，但不作为唯一防线。

## 四、实测验证

| 场景 | 行为 | 结果 |
|---|---|---|
| "查一下相关事件" | 门控拦截，零模型调用 | 标准问句 + 4 个胶囊选项，"事件"正确映射重点工作 |
| 模拟正文清单后回"1" | 数字改写为完整查询 | 真实调用工具（2 步），无编造 |
| "这周有什么会议"（回归） | 正常走模型 | 真实会议数据（学院班子会议 17-408） |
| "查一下"（回归） | 门控问模块 | 三个带默认时间的模块选项 |

## 五、可复用的设计要点

1. **意图门控模式**：自然语言入口处先用廉价的规则引擎（关键词/正则）分流，规则能处理的绝不进大模型——省 token、省时延、行为确定；
2. **改写而非拒绝**：数字"1"、省略式"那任务呢"这类用户自然行为，后端**改写成模型能正确理解的完整指令**，而不是要求用户换说法；
3. **输出侧校验**：对"声称有数据"的回答核对其数据来源（本轮是否调用过工具），无源即判编造——宁可诚实说没有，不放猜测出去；
4. **分层防御**：提示词（降概率）→ 门控（绕开）→ 改写（纠正输入）→ 校验（拦截输出），任何一层失效其余层仍能兜住；
5. **排查幻觉的方法**：查后端日志中该轮是否有工具调用记录（`GLM响应` 的 `finish_reason` 与中间轮次），再拿回答中的关键实体去数据库核对——两步就能定性。
