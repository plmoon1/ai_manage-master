# 单轮对话删除功能 · 代码讲解

> 适用版本：2026-08-30
> 功能：在 AI 助手对话中，删除**某一轮问答**（用户提问 + AI 回答），会话内其他轮次保留；删空所有轮次时连带删除会话。
> 本文按"一次删除点击的完整旅程"逐层讲解，适合作为学习前后端交互的示例。

---

| 层 | 文件 | 职责 |
|---|---|---|
| 前端页面 | `task-miniprogram/src/pages/ai/ai-chat.vue` | 聊天界面、删除按钮、确认弹窗、本地消息列表维护 |

## 二、先理解数据模型：什么叫"一轮"

数据库表 `ai_chat_message` 里，**每条消息是一行**：

```
id(UUID主键) | sid(会话id) | role(user/assistant) | content | seq(自增序号)
```

每问一次，`saveTurn()` 会**成对插入两行**：提问（role=user）+ 回答（role=assistant），两行 seq 连续递增。

```java
// AiChatService.saveTurn() —— 一轮 = 两条消息一起入库
private JSONObject saveTurn(String sid, String question, String answer) {
    List<AiChatMessage> msgs = new ArrayList<>();
    AiChatMessage q = new AiChatMessage();
    q.setId(UUID.randomUUID().toString());
    q.setSid(sid); q.setRole("user"); q.setContent(question);
    msgs.add(q);
    AiChatMessage a = new AiChatMessage();
    a.setId(UUID.randomUUID().toString());
    a.setSid(sid); a.setRole("assistant"); a.setContent(answer);
    msgs.add(a);
    aiChatMessageMapper.insertBatch(msgs);
    // 返回两条消息的id，随 done 事件推给前端（供逐轮删除定位用）
    return JSONUtil.createObj().set("userMsgId", q.getId()).set("aiMsgId", a.getId());
}
```

所以"一轮"在数据库里**没有单独的表**，它就是相邻的两行——这就是删除逻辑的核心是"从一条 user 消息删到下一条 user 消息之前"，而不是删"某个 id 对应的一条记录"。

## 三、前端：按钮怎么来的，点击后发生什么

### 3.1 按钮的显示条件（模板部分）

```html
<!-- 用户消息气泡下方 -->
<text
  v-if="m.role === 'user' && m.id && !loading"
  class="round-del"
  @tap.stop="removeRound(index)"
>删除</text>
```

三个条件各有含义（防御式写法）：

- `m.role === 'user'`——删除入口只挂在**用户消息**上（一轮的锚点），AI 消息不挂；
- `m.id`——消息必须已落库拿到 id。刚发出的消息本地先显示、后端还没保存完时没有 id，此时不显示删除，防止删一个服务端不存在的东西；
- `!loading`——AI 正在回答时禁止删，避免流式回答进行到一半时数据错乱。

`@tap.stop` 的 `.stop` 是阻止事件冒泡——这个 text 在消息行里，不阻止会同时触发父级的事件。

### 3.2 消息的 id 从哪来（两个来源）

前端的消息数组 `messages` 有两条产生路径：

**路径 A：加载历史**。`loadSession()` 调 `GET /ai/messages`，后端返回的消息对象自带 id，映射时保留：

```js
this.messages = list.map((m) => ({ id: m.id, role: m.role, content: m.content }))
```

**路径 B：刚发的新消息**。`send()` 先把消息 push 进界面（乐观更新），此时 id 是空的；等后端处理完、SSE 推来 `done` 事件时把 id 补回去：

```js
// handleAiEvent 的 done 分支
const um = this.messages[aiIndex - 1]   // AI占位消息的前一条就是本轮用户消息
if (um && um.role === 'user' && evt.userMsgId) um.id = evt.userMsgId
if (evt.aiMsgId) m.id = evt.aiMsgId
```

配套地，后端在 `done` 事件里新增了 `userMsgId` / `aiMsgId` 字段（`AiChatService.chatStream`），把 `saveTurn()` 生成的 UUID 传回来。

**Vue2 的经典坑**：如果 push 的对象一开始没有 `id` 属性，事后 `um.id = xxx` 赋值**不会触发界面更新**——Vue2 的响应式系统在对象创建时"拍快照"记录属性，后加的属性不在快照里。所以 `send()` 必须预先声明：

```js
this.messages.push({ id: null, role: 'user', content: message })  // id 先占位
```

这样后续赋值才是响应式的，`v-if="m.id"` 才会立即生效。（Vue3 没这个问题，本项目是 Vue2。）

### 3.3 点击删除后（removeRound 方法）

```js
removeRound(index) {
  const m = this.messages[index]
  if (!m || m.role !== 'user' || !m.id || this.loading) return   // 方法内再验一次（双保险）
  uni.showModal({                                                 // 1. 二次确认
    title: '删除这轮对话',
    content: '确定删除这条提问和AI的回答吗？删除后不可恢复',
    success: async (r) => {
      if (!r.confirm) return
      try {
        await aiApi.deleteMessage(this.sessionId, m.id)           // 2. 调后端
        // 3. 本地同步删除：从这条user消息起，删到下一条user消息之前
        let end = index + 1
        while (end < this.messages.length && this.messages[end].role !== 'user') end++
        this.messages.splice(index, end - index)
        // 4. 删空了 → 会话已被后端连带删除，前端重置状态
        if (this.messages.length === 0) {
          this.sessionId = null
          this.scrollTop = 0
        }
        uni.showToast({ title: '已删除', icon: 'success' })
      } catch (e) {
        // 错误提示由 request 拦截器统一处理
      }
    }
  })
}
```

第 3 步的要点：**前端本地删的规则和后端数据库删的规则必须是同一套**（"user 消息到下一个 user 之前"），界面和服务端才能保持一致，删完不需要重新拉取——这是"乐观更新"思路：相信请求会成功、直接改本地，失败了走 catch 回滚提示。

### 3.4 接口封装（api/index.js）

```js
// 删除某一轮问答（mid=该轮用户消息id，连带AI回答一起删除）
deleteMessage(sid, mid) {
  return request({
    url: '/ai/message',
    method: 'DELETE',
    params: { sid, mid }
  })
}
```

走统一的 `request` 封装，自动带 token 请求头、统一错误 toast。

## 四、后端：请求进来后的三层流水线

### 4.1 Controller——只做"接待"，不做业务

```java
@DeleteMapping("/message")
public Result deleteMessage(@RequestParam String sid, @RequestParam String mid) {
    try {
        aiChatService.deleteMessageRound(sid, mid);
        return Result.success();
    } catch (Exception e) {
        return Result.error("403", e.getMessage());
    }
}
```

只负责：解析 URL 参数（`?sid=会话id&mid=消息id`）→ 调 Service → 包成统一的 `Result` JSON。业务逻辑一律下沉到 Service——这是 Spring 项目的标准分层：**Controller 管协议，Service 管业务，Mapper 管 SQL**。

### 4.2 Service（deleteMessageRound）——核心业务三步走

**第一步：权限校验——这个会话是不是当前登录用户的？**

```java
User user = TokenUtils.getCurrentUser();   // 从请求头的JWT解析，不信任前端
AiChatSession session = aiChatSessionMapper.getByIdAndUid(sessionId, user.getId());
if (session == null) {
    throw new IllegalArgumentException("会话不存在或无权访问");
}
```

当前用户是谁？**由服务端从 token 推导，绝不信任前端传的"我是谁"**——否则任何人改个参数就能删别人的对话。`getByIdAndUid` 把 `where id=? and uid=?` 写进 SQL，查不到就说明不是你的，直接拒绝。

**第二步：定位这一轮——从目标 user 消息起，删到下一轮 user 消息之前**

```java
List<AiChatMessage> all = aiChatMessageMapper.listBySid(sessionId);  // 已按seq升序
List<String> toDelete = new ArrayList<>();
boolean started = false;
for (AiChatMessage m : all) {
    if (!started) {
        if (m.getId().equals(messageId)) { started = true; toDelete.add(m.getId()); }
        continue;
    }
    if ("user".equals(m.getRole())) break;   // 碰到下一轮的提问就停
    toDelete.add(m.getId());                 // 中间的都是这轮的回答，纳入
}
if (toDelete.isEmpty()) {
    throw new IllegalArgumentException("消息不存在");
}
```

单次线性扫描：整个会话的消息按 seq 排好，找到起点后开始收集，遇到下一个 user 就刹车。

为什么不是"删 mid 和它的下一条"？——不依赖"一轮恰好两条"的假设。以后若一轮存多条消息（比如把中间步骤也落库），这段代码不用改。**写业务代码时给数据格式的演进留余地。**

**第三步：执行删除 + 兜底清理**

```java
aiChatMessageMapper.deleteByIds(toDelete);               // 消息物理删除
if (aiChatMessageMapper.countBySid(sessionId) == 0) {    // 会话删空了
    aiChatSessionMapper.softDelete(sessionId, user.getId());  // 连会话一起软删
}
```

对称设计：**消息物理删**（`delete from ...`，数据真没了，不留敏感聊天内容），**会话软删**（只改 `isdelete` 标记）。删空消息后若不管会话，历史列表会剩一个空壳"新对话"——所以补这个兜底。

### 4.3 Mapper + XML——SQL 长什么样

Java 接口只声明方法，真正的 SQL 在 XML（MyBatis 惯例）。本次新增三个方法：

```xml
<select id="getById" resultType="com.qzb.springboot.entity.AiChatMessage">
    select id, sid, role, content, create_time as createTime
    from ai_chat_message where id = #{id}
</select>

<delete id="deleteByIds">
    delete from ai_chat_message where id in
    <foreach collection="ids" item="id" open="(" separator="," close=")">
        #{id}
    </foreach>
</delete>

<select id="countBySid" resultType="int">
    select count(*) from ai_chat_message where sid = #{sid}
</select>
```

`<foreach>` 把 id 列表拼成 `delete ... where id in ('a','b')`。`#{id}` 是**预编译占位符**，走 PreparedStatement，传入值永远当数据、不会当 SQL 执行——这是防 SQL 注入的根本机制（**拼接永远用 `#{}`，不要用 `${}`**）。

## 五、整个链路串起来

```
点「删除」→ showModal 二次确认
         → axios DELETE /ai/message?sid=&mid=   （request.js 拦截器自动带 token 头）
         → JwtInterceptor 校验 token、解析出当前用户
         → AiChatController.deleteMessage()
         → AiChatService.deleteMessageRound()
              ├─ 鉴权：会话属于当前用户吗？
              ├─ 扫描：定位这一轮的所有消息 id
              ├─ Mapper.deleteByIds() 物理删除
              └─ 删空则软删会话
         ← Result{code:"200"}
前端 splice 本地数组 → 界面立即更新（不需要重新拉取）
```

## 六、值得记住的设计点

1. **身份从 token 推导**：凡是"我的 xx"类操作，用户身份一律服务端从 JWT 解出，前端只传业务 id（sid/mid），越权自然被拦。
2. **轮次的隐式结构**：一轮 = 相邻的 user/assistant 消息对，用 seq 排序界定边界，删除算法不依赖"恰好两条"。
3. **乐观更新**：前端按与服务端相同的规则同步改本地，省一次回拉；失败统一走拦截器提示。
4. **Vue2 响应式**：后补的对象属性不响应，需在创建时预声明 `id: null`。
5. **物理删 vs 软删**：内容数据物理删（不留敏感内容），结构性数据软删（保留痕迹）。
6. **防御式条件**：`v-if` 三条件 + 方法内再校验，界面和逻辑双保险。
7. **`#{}` 而非 `${}`**：MyBatis 防注入的铁律。
